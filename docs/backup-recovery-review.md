# Backup recovery review and verification

A separate review followed the implementation and first round-trip tests. It traced error and interruption paths independently from the success path.

| Area | Finding and resolution | Evidence |
| --- | --- | --- |
| Partial commits | Original restore cleared/wrote stores and databases separately. A later failure could leave mixed project, summary, stash and photo state. Replaced with isolated database generations and one publication pointer including portable settings. | Quota injection in project staging, stash staging after project commit, settings staging, and final pointer publication; current semantic state survives reload. |
| Attachments and orphaned blobs | Tracing pictures and active-session checkpoints were excluded. Photo restore swallowed failures, and replacing photos could remove unrelated device pictures. Export now inventories project-owned photos, thumbnails, traces and checkpoints. Import validates owners, pairs, sizes and manifest; additive restore retains destination records. Durable staging manifests permit abandoned Blob databases to be collected after interruption. Blocked deletion retains its manifest for retry. | Fresh-profile byte equality; missing attachment rejection; interrupted page after first staged database commit, then cleanup to zero abandoned restore databases; photo unit round trip retains extra destination pictures. |
| Accidental replacement | Duplicate project, library, attachment and accounting IDs previously overwrote device data. Conflicting IDs now abort the entire import; equal records are skipped, independent inventory/library keys merge without summing stock. The legacy auto-save alias and destination Sync baseline take precedence over incoming equivalents. | Conflicting-project test and repeated identical import; accounting reference and deduction checkpoint comparison. |
| Unsafe archives | Original inflate had no expansion budget and nested validation was shallow. Input/expanded data now has a 64 MiB budget; unknown stores/databases, unsafe object keys, duplicate record keys, malformed specialised marks, invalid base64/owners/dimensions, unsupported project/archive versions and integrity failures are rejected before staging. No archive entry becomes a filesystem path or fetched URL. | Compressed expansion limit and pre-read oversized-file rejection; unsafe-object/store/mark tests; corruption and future-version tests. |
| False completeness | Photo/settings errors could still produce restore success. JSON could turn typed completion arrays into plain objects. Staging failures now propagate, and typed arrays/Map/Set data are normalised before validation and sealing. Unexpected binary data outside attachment storage refuses export. Success copy describes a download request rather than claiming the user retained a file. | Typed progress JSON/CSB regression and semantic duplicate checks; failed-save and active-session-checkpoint tests retain backup timestamp until recovery. |
| Interrupted publication | A restore could resume local saves after a fixed 30 seconds, and a refusal in a stale tab could clear its saving guard. Live write transactions now stay blocked until reload after publication; failure only unblocks the current generation. | Stale-tab export/restore refusal and persistent write guard; simulated interruption before publication. |
| Early navigation and pending settings | Early page redirects could read the original active-project pointer before routing was installed. Pending slider timers could overwrite imported settings. Routing now loads in the head before redirects; portable timers are cancelled at publication. Snapshot opt-in baselines remain stable for identical imports. | Entry-page wiring, fresh-profile reload, pending-timer/Storage enumeration/sessionStorage regression, repeated import with automatic snapshots enabled. |
| Migration compatibility | An empty destination's current stash marker must not suppress migration of old imported threads. Imported stash rows use the existing pure v2/v3 transformations while still staged. Project compact-grid records remain intact and the normal project migration marker is reset. | Frozen v1 JSON and CSB fixtures with a v8 compact chart, photos, old bare thread IDs, library/project references and deduction accounting. |

The existing reminder browser cases and persistence requests are retained. The previous failed-small-write browser expectation was updated because an active timer checkpoint now participates in the full project transaction: a failed checkpoint must refuse export until storage recovers, rather than claim a complete archive.

## Practical limits

Staging and retained previous generations need additional browser storage. Safe restore requires Web Locks and a reload; older browsers receive an explicit update-browser error. CRC32 detects accidental corruption, not malicious authorship. Legacy v1 files have no completeness proof and are labelled accordingly. Current-device Sync setup and baselines are retained; no automatic sync service is added. Browser eviction, cleared site data and hardware failure beyond the browser storage API are outside these guarantees.
